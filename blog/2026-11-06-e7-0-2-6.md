"A strict subset of TypeScript" is only a promise if you can check it. [E7 0.2.6](https://github.com/e7lang/e7/releases/tag/v0.2.6)
writes the subset down and makes CI check it. It is compatible with 0.2.5 in both directions: the bytecode and the C
API did not change.

<!-- truncate -->

## What defines E7

There is no official "strict TypeScript" standard. TypeScript is defined by its compiler, so E7 now pins three things
([SPEC section 0.1](/docs/reference/SPEC)):

- **The upper bound is `tsc` 5.6** with `strict` and `exactOptionalPropertyTypes`. Every E7 program must type-check
  there, and CI checks every test and example.
- **Run-time behaviour is ECMAScript as Node.js 22 implements it.** CI compares output byte for byte, and a
  differential fuzzer compares random programs.
- **Three rules decide what is in.** Types are known at compile time, the bytecode is verifiable, and behaviour is
  identical to JavaScript. The first is fixed: a feature that needs run-time type information stays out of E7, however
  common it is in TypeScript.

## 250 features, each one a test

The new [TypeScript coverage table](/docs/reference/TYPESCRIPT) goes through the TypeScript Handbook chapter by
chapter, plus the JavaScript syntax and standard library: 250 features, with what E7 does with each, why, and what to
write instead. Every row is a small program. CI compiles it with E7, compares its output with Node.js when the
feature is supported, checks that E7 rejects it with the stated error when it is not, and type-checks all of them
with `tsc`. The table is generated from those programs, so it cannot drift from the compiler.

Writing it found compiler gaps. They are fixed in this release:

```ts
interface Plugin { name: string; init?(): string }       // optional methods
function total(xs: readonly number[]): number {           // readonly is checked, as in tsc
  return xs.reduce((a, b) => a + b, 0);
}
function scale(n: number, by = n * 2): number { return by; }  // defaults may use earlier parameters
enum Op { Add, Mul }
function apply(op: Op, a: number, b: number): number {
  switch (op) {                                            // exhaustive: no default needed
    case Op.Add: return a + b;
    case Op.Mul: return a * b;
  }
}
function run(p: Plugin, list: number[] | null): string {
  const fact = (n: number): number => (n <= 1 ? 1 : n * fact(n - 1));  // recursive local functions
  if (list === null) list = [];                            // narrowing survives the if
  return p.name + (p.init?.() ?? "") + fact(5) + total(list) + scale(1) + apply(Op.Mul, 2, 3);
}
```

E7 used to accept two kinds of program that `tsc` rejects: writes through `readonly` arrays and properties, and
setting an optional property to `undefined` (under `exactOptionalPropertyTypes`). Both are compile errors now. Unsupported
TypeScript, such as type predicates, decorators and conditional types, now gets an error that names the feature.

## Security review

An independent review of the 0.2.5 VM changes found no memory-safety issue, but found six ways to make the host spend
more time or memory than its limits allow. The worst was a 0.2.5 regression: with time slicing on, one `pbkdf2` or
`assertEqual` call could hold the host thread without bound. All six are fixed with regression tests
([verification record, section 3.6](/docs/reference/PRODUCTION)).
