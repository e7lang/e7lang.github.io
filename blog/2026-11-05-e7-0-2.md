[E7 0.2.0](https://github.com/e7lang/e7/releases/tag/v0.2.0) is the release we want the first production pilots
to run. It makes the incompatible changes we could see coming now, so that the 0.2.x line can stay compatible:
modules compiled by any 0.2.x compiler run on every 0.2.x VM.

<!-- truncate -->

> **Update: 0.2.1.** The same day, an independent review of the new try/catch found no memory-safety issue but eight
> problems, among them three ways to make a script use far more CPU time than its instruction budget allows (a
> crafted handler table, library functions failing in a loop, and deep throws). All are fixed in
> [0.2.1](https://github.com/e7lang/e7/releases/tag/v0.2.1), along with a debugger option to stop on caught errors;
> the findings are listed in the [verification record](/docs/reference/PRODUCTION). Use 0.2.1 rather than 0.2.0.

## try / catch

E7 scripts can now catch errors:

```ts
function ratio(a: bigint, b: bigint): string {
  try {
    return (a / b).toString();
  } catch (e) {
    if (e instanceof RangeError) return "undefined (" + e.message + ")";
    throw e;
  }
}
console.log(ratio(10n, 3n), ratio(1n, 0n)); // 3 undefined (Division by zero)
```

The catch variable is `unknown`, as with TypeScript `--strict`, so you narrow it with `instanceof Error` before
reading `.message`. What can be caught is deliberately limited to **errors that Node.js also throws**: your own
`throw`, `JSON.parse` syntax errors, and the standard library's `RangeError`, `TypeError` and `URIError`. E7's own
checks, such as an out-of-bounds read (where JavaScript returns `undefined`) or a `JSON.parse(text) as T` shape
mismatch, still end the call. Catching them would make the same program print different things on E7 and on
Node.js, and "an E7 program behaves like the TypeScript it is" is the promise we keep. `throw` now takes Errors
only; `finally` is not supported yet.

In the VM, each function carries a table of handler ranges that the bytecode verifier checks like everything else.
A failed handler table is rejected at load time, so a malicious module cannot jump into the middle of an
instruction through a crafted handler.

## Modules say which VM they need

Apps stay in the field for years, and the server will compile modules for app versions it has never seen. Every
module now records the oldest e7vm that can run it, computed from the instructions and functions it actually uses.
An older app rejects a module it cannot run with a clear `E7_ERR_VERSION` instead of a verifier error, and
`e7c --target 0.2` turns newer features into compile errors, so you can build for the oldest app you still serve.
`e7c --info` and `e7_inspect()` read a module's header without loading it.

0.1 modules must be recompiled: the bytecode format moved to version 2. A corpus of modules compiled by released
compilers is now part of CI, and it checks exactly that promise.

## Shipping modules over the air

`E7ModuleManager` (Kotlin/Java and Swift) implements the delivery flow we kept describing in prose: a signed
manifest, a percentage rollout by user, a kill switch that falls back to the script bundled with the app, a
`selfTest()` before a new module goes live, and automatic rollback to the last good version after repeated
failures. [Deployment](/docs/reference/DEPLOYMENT) walks through keys, manifests, rollout and how to size the
instruction budget and memory limit from measurements.

## Gates

- `e7 --stats` and `e7_gc_stats_get()` report instruction ticks, GC pauses and the peak heap. CI compares the
  ticks and peak heap of every benchmark exactly against a baseline, and the interpreter's machine instruction count
  against a 3% tolerance.
- A new fuzzer calls every crypto and encoding function with arguments generated from their signatures and checks
  round-trip properties (encrypt then decrypt, sign then verify, ...).
- Every release file and package now has a GitHub build provenance attestation and an SPDX SBOM.

## Still true

E7 is 0.x: it has been tested and hardened, but it has not run in production yet, and its security reviews were
done by AI review agents, not a third-party auditor. If you have a script that should change without an app
release, we would like to hear about it: that pilot is the next step.
